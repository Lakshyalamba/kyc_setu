# Retention policy

This page says, in plain English, what KYC Setu keeps, for how long, why, and how a person can ask for something to be
deleted. The periods below are configuration in `packages/shared/src/retention.ts`; if a period changes there it must change
here too.

> **Status.** The periods are written down and a **dry run** reports what each would remove (`POST /admin/retention/dry-run`,
> lead only). **Nothing is purged yet and nothing is scheduled.** A real purge needs a legal sign-off and a deletion
> procedure that respects the audit chain; both are still to do. Until then everything below is retained.

## What is kept, and for how long

| What                                         | How long                      | Why                                                                                                                                                                  |
| -------------------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity documents (PAN, Aadhaar, signature) | 7 years after the decision    | Banks and regulators may ask to see the documents behind a KYC decision for years afterwards.                                                                        |
| Raw text read from documents by OCR          | 90 days after it was read     | It exists to debug the reader and to compare what you typed with what is printed. The structured fields are what the decision uses, so the full text is short-lived. |
| Face embeddings                              | 7 years after the decision    | To show how a face match was reached if the decision is questioned. **Not stored yet**: there is no selfie step.                                                     |
| Selfie and liveness frames                   | 7 years after they were taken | Evidence for the liveness and face-match checks. **Not stored yet.**                                                                                                 |
| The audit log and its daily hash chain       | Indefinitely                  | It is the evidence that everything else was handled properly. It holds identifiers and actions, not documents or typed details, and it can only be added to.         |
| The text of each consent you accepted        | Indefinitely                  | What you agreed to must stay exactly as you saw it, however the wording changes later. It is not personal data about you.                                            |

"The decision" means the officer's final approval or rejection. An application that is still being reviewed has no
decision yet, so its documents are not yet counting down.

## What is not kept

- The full Aadhaar number is never stored in the clear. It lives encrypted and is shown to an officer only when they ask,
  each time being recorded.
- Passwords are stored only as a salted hash.
- A one-time code is stored only as a hash, and expires in minutes.
- Signed links to your documents last five minutes; links to an audit packet last an hour.

## Asking for something to be deleted

You can ask your bank (the data controller) to delete your data. What happens next depends on what you ask about:

- **Raw OCR text** can be deleted on request at any time; it does not affect your decision record.
- **Documents and face data** are kept for the period above because the law asks the bank to keep KYC records. A request
  inside that period is answered with the date it becomes deletable, unless the law allows earlier deletion.
- **The audit log** is not deleted: it is evidence, it holds no documents or typed details, and rewriting it would break the
  hash chain that proves it has not been tampered with. Where it names you, it does so by an identifier.

To ask, contact the bank's grievance officer named in the consent text you accepted. They will pass the request to an
operator, who records it. There is no self-service deletion yet.

## How the periods are enforced (when they are)

1. A scheduled job (`retention-sweep`) will, for each data class, find what is past its period using the clock in the table
   (decision, extraction, capture).
2. It will first run as a dry run and log the counts, as it does today, so an operator can see what a purge would do.
3. A purge will delete the stored object and its encrypted copy, leave the row that says it was deleted and when, and write
   an audit entry. The audit log and its chain are never touched.

## The signing key for audit packets

Session packets exported for auditors are signed with an Ed25519 key. **In development that key is a file generated by
`make up` in `infra/dev-keys/` (git-ignored) and it is not secure.** In production it must be held in an HSM or wrapped by
a KMS, rotated on a schedule, and its public key published; the application refuses to start an export without a
provisioned key when `NODE_ENV=production`. The key's fingerprint is written to the audit log with every export, so a
packet that carries a different key is detectable.
