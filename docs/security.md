# Security

A short-form threat model: what is protected, from whom, how, and where the protection stops. It is written for a reviewer, so
it says plainly what this project does **not** do.

> **This is a KYC-style workflow for demonstration. It has not been audited or penetration-tested, and nothing here is a claim
> of compliance with any regulation or standard.** The decisions below are the ones a real deployment would start from, not
> the ones it could stop at.

## What is worth protecting

| Asset                                           | Why it matters                                                         |
| ----------------------------------------------- | ---------------------------------------------------------------------- |
| Document images (PAN, Aadhaar, signature)       | Enough to impersonate a person                                         |
| Typed identifiers (PAN, Aadhaar, date of birth) | The same                                                               |
| The decision (and what the officer saw)         | It is the product; changing it silently is the worst integrity failure |
| The audit trail                                 | The evidence that everything else was handled properly                 |
| Staff sessions                                  | One officer's cookie can read applications and decide them             |

## Where the data is, and how it is locked

| Data                                | Where                                           | Protection                                                                                                                                                                                    |
| ----------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Document files                      | S3-compatible bucket, **private**               | AES-256-GCM per file, with a fresh data key each time. The key is wrapped by the KMS and stored on the `documents` row. The API refuses to boot if the bucket has an anonymous-access policy. |
| Personal details                    | `kyc_sessions.personalDetails` (Postgres JSONB) | Each sensitive field is AES-256-GCM encrypted under `PII_ENCRYPTION_KEY` before it reaches the database                                                                                       |
| OCR text                            | `extractions.rawTextEncrypted`                  | Envelope-encrypted like documents; kept 90 days                                                                                                                                               |
| "Same PAN as an approved customer?" | `extractions.panNumberHmac`                     | HMAC-SHA-256 under a key derived (HKDF) from the PII key. The PAN is not stored in the clear to answer it                                                                                     |
| Passwords, one-time codes           | `users`, `otp_challenges`                       | Argon2id; a sign-in for an unknown e-mail still burns a hash so timing does not reveal who has an account                                                                                     |
| Session cookie                      | the browser                                     | A signed JWT (HS256, 24 hours) in an `HttpOnly`, `SameSite=Lax` cookie, `Secure` in production. Customers and staff have separate cookies                                                     |
| Audit packets                       | a second private bucket                         | Signed with Ed25519; links last one hour; every link issued is audited                                                                                                                        |

**Keys, development versus production.** In development the master key that wraps data keys is an environment variable
(`KMS_LOCAL_MASTER_KEY`) and the audit-packet signing key is a file generated by `make up`. That is convenient and **not
secure**: the key sits next to the data. The application enforces the difference: it refuses to start in production with the
local KMS, and requires a signing key file there. The production KMS client (`AwsKmsClient`) is a stub: it exists to show the
seam (`generateDataKey`, `decryptDataKey`, a `keyId` stored with every wrapped key so rotation is possible), and **nothing
real is wired to it**. There is no key rotation procedure yet.

## Who may do what

Authorisation is a table of permissions per role, in [`packages/shared/src/rbac/permissions.ts`](../packages/shared/src/rbac/permissions.ts), and
every route asks for a named permission through one guard (`requirePermission`). A test walks every mounted route and fails for
one that is neither guarded nor on a short, reasoned allowlist, and another runs every guarded route as every role. A denial
is a 403 that names the missing permission, and is written to the audit log. The matrix is in the
[README](../README.md#access-control).

What each role never sees:

- **Customers**: anything about risk beyond a single word (the band), anyone else's application, any officer's note except one
  written to be read by them.
- **Officers**: a full Aadhaar number unless they ask (each ask is audited with who, when and which session), and no identifier
  unmasked in any list or payload.
- **Auditors**: the Aadhaar reveal and any write at all. They can read everything else, search every application, and export.
- **Masking is in one function** (`maskForRole`), and a test calls every GET route as every role against a fully populated
  application and fails on a raw identifier. It found a real leak once (a development route showing a PAN to the auditor).

## Threats (STRIDE, short form)

| Threat                     | Example                                                         | What stands in the way                                                                                                                                                                                                       | What is left                                                                                                                                |
| -------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **S**poofing               | Guess or stuff a password                                       | Argon2id; five wrong passwords lock an account for 15 minutes (423); per-address and per-account request limits in Redis; separate cookies for customers and staff                                                           | No MFA, no e-mail verification, no password reset. Limits are off outside production by default (they are on in production)                 |
| Spoofing                   | Use a document link meant for someone else                      | A link is a random id plus an HMAC over (document, purpose, recipient, expiry), checked against the database row; five-minute life; the caller must also be signed in as the person it was issued to                         | A leaked link works for its five minutes for that person only                                                                               |
| **T**ampering              | Upload a file that is not what it claims                        | The type is read from the bytes, not trusted; a declared/actual mismatch is refused; 5 MB cap enforced while streaming; only JPEG, PNG, PDF; the bytes never touch disk                                                      | No virus or malware scan. OCR libraries parse hostile images (a risk, mitigated only by running them in a container)                        |
| Tampering                  | Change a past decision or audit row                             | Database triggers refuse `UPDATE` and `DELETE` on decisions, risk assessments, audit rows, chain checkpoints and published consent; the application's database client has no update or delete for the audit log              | A database superuser can disable a trigger. See "The audit chain" below                                                                     |
| **R**epudiation            | "I never approved that"                                         | Every decision, claim, reveal, export, denial and sign-in is an audit row with actor and time; the decision stores a frozen snapshot of what the officer saw                                                                 | The log records what the application did. It cannot prove who was at the keyboard behind a valid cookie                                     |
| **I**nformation disclosure | A list or payload shows an identifier                           | Encryption at rest as above; masking in one serialiser with a route-by-route leak test; logs and Sentry events scrub identifiers, cookies and request bodies on `/kyc/*`                                                     | Identifiers are in memory while a worker or an officer's request handles them. No field-level access logging in the database                |
| Information disclosure     | A bucket opened to the world by mistake                         | The API checks the bucket policy on boot and refuses to start if it grants anonymous access; objects are reachable only through the API                                                                                      | Whoever holds the storage credentials can read ciphertext; they still need the KMS to read it                                               |
| Information disclosure     | The AI service fetching an attacker's URL (SSRF)                | It will only fetch from configured origins, only `/files/` paths, no redirects, no credentials in the URL, bounded size and time; every call needs a shared secret (`X-Internal-Key`); the link it is given lives 60 seconds | The shared secret is one value in an environment variable                                                                                   |
| **D**enial of service      | Flood sign-in or OTP; upload huge files                         | Rate limits; upload cap; JSON body cap 100 KB; OTP sends are capped per user                                                                                                                                                 | One API process and one worker; nothing absorbs a real flood. Reading a document costs seconds of OCR, so uploads are the expensive request |
| **E**levation of privilege | A customer calls a staff route; an officer calls an audit route | One guard on every route; conformance and cross-role tests; a customer cookie is not accepted on staff routes                                                                                                                | Roles are fixed per account: no review of who holds `OFFICER_LEAD`, no break-glass, no four-eyes on a decision                              |

### Cross-site request forgery

There are no CSRF tokens. The defence is `SameSite=Lax` cookies (a cross-site `POST` carries none), request bodies that are
JSON or multipart only, and a single allowed CORS origin with credentials. That is a deliberate, reviewed trade for the
current shape of the application and is on the list of things to revisit before anything real.

### Sessions cannot be revoked

A session is a stateless JWT. Signing out clears the cookie and writes an audit row, but a copied cookie stays valid until
it expires (24 hours). Closing that gap means a server-side session list; it is not built.

## The audit chain: what it protects and what it does not

Each audit row is hashed; each IST day's rows are chained, each day's chain starts from the previous day's hash, and the result
is stored in a table that also refuses updates. The nightly job (00:05 IST) chains every closed day; `GET /audit/chain/verify`
recomputes the range and reports, per day, **PASS or FAIL naming the first row that is MODIFIED, MISSING or UNEXPECTED** (added
after the day closed), or a broken link between days.

It **does** make changes made _behind the application's back_ detectable: someone with database access who disables the
trigger and edits a row, deletes one, or inserts one into a closed day. The tests do exactly that (with
`session_replication_role = replica`) and check the day and row are named.

It **does not**:

- stop that person. It makes them noticed, after the next verification, and only if verification is run and someone looks.
- protect today: the current day is not chained until it closes.
- protect against someone who can rewrite the log, the checkpoint table **and** recompute the chain together. The chain is not
  anchored anywhere outside the database (no external timestamp, no printed hash, no second system). Publishing each day's hash
  somewhere the database owner cannot reach would close that, and is the obvious next step.
- say anything about whether what was logged was _true_, only that it has not changed since.

The signed audit packet for a session has the same honesty: its Ed25519 signature proves the packet has not changed since
it was built, by the holder of the signing key. In development that key is a file anyone with the repository's working directory
can read.

## Not built, on purpose or not yet

| Gap                                                                      | Why it matters                                                                             |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| A real KMS and key rotation                                              | Today the master key is an environment variable                                            |
| An HSM-backed signing key for audit packets                              | Today it is a file                                                                         |
| MFA and e-mail verification for staff                                    | A password is all that stands between the internet and the review queue                    |
| Server-side session revocation                                           | See above                                                                                  |
| Virus scanning of uploads                                                |                                                                                            |
| CSRF tokens                                                              | See above                                                                                  |
| An external anchor for the audit chain                                   | See above                                                                                  |
| Real liveness and deepfake resistance                                    | There is no selfie step, so there is nothing to defeat                                     |
| A real purge for retention                                               | The periods are written down; nothing deletes ([retention-policy.md](retention-policy.md)) |
| Penetration testing, threat-model review by someone who did not build it | This document is the author's view of their own work                                       |
